# 入库后货件二维码预取机制

> 适用范围：ERP 后端 `erp-backend-lite`（`order-process.js`）
> 最后更新：2026-11-10

## 1. 背景与目标

扫描打单（`scan-ship/submit`）时需要读取面单 PDF 并解析条码（`op_posting_barcode`），打印页需要 `waybill-cache` 里的 PDF。而 Ozon `packageLabel` 对面单装配中的货件（`awaiting_registration`）会耗时 45~60 秒，且对状态不允许的货件抛 `INVALID_ARGUMENT`。

**目标**：在入库动作把货件推进到 `awaiting_registration` / `awaiting_deliver` 的瞬间，后台立即（fire-and-forget）拉取面单 PDF 缓存到本地（`waybill-cache` + `op_posting_barcode`），让后续扫描打单无需再等待 Ozon 装配、无需现场解析。

## 2. 触发时机（ship 路由三处出口）

`POST /admin/api/order-process/ship`（入库）成功路径有三处，均调用：

```js
fireAndForgetBarcodePrefetch(row.storeId, row.postingNumber);
```

| 路径 | 位置 | 说明 |
|---|---|---|
| 幂等返回 | `row.operateStatus` 已在 `['wait_stick','wait_dispatch','dispatching','delivering','signed']` 且 Ozon 是 `awaiting_registration/awaiting_deliver` | 本地已入库，直接预取 |
| 竞态容错 | `HAS_INCORRECT_STATUS` 后重新查询，`stNow` 在入库后状态链 | 另一请求已入库成功，补预取 |
| 轮询成功 | 指令提交后 Ozon 状态离开 `awaiting_packaging`（`newStatus` 变化） | 主成功路径 |

## 3. 预取流程（fire-and-forget）

```
ship 成功
  → fireAndForgetBarcodePrefetch(storeId, postingNumber)
      → enqueueBarcodePrefetch (Map 去重 key=storeId|postingNumber)
      → pumpBarcodePrefetch（全局并发信号量 MAX_CONCURRENCY=3）
          → runBarcodePrefetch
              → doBarcodePrefetch:
                  1. 查 op_posting_barcode 已有 lower_barcode → 直接完成
                  2. packageLabel(store, [postingNumber]) 拉面单 PDF
                  3. setWaybill(storeId, [postingNumber], buffer) 缓存 PDF
                  4. extractWaybillBarcodes(buffer) 解析条码
                  5. upsertPostingBarcode 落 op_posting_barcode
```

### 3.1 去重与队列

- `barcodePrefetchState`（Map）：`storeId|postingNumber` → `{ retries, timer }`，同一货件只允许一个预取任务在途/等待重试；
- `barcodePrefetchQueue`：待执行任务队列；
- 全局 `barcodePrefetchActive` 信号量控制并发 ≤ 3，任务完成（成功/放弃）后自动 `pump` 下一个。

### 3.2 重试策略（用户确认参数）

- **重试间隔**：15 秒（`BARCODE_PREFETCH_RETRY_INTERVAL_MS = 15 * 1000`）
- **最多重试**：10 次（`BARCODE_PREFETCH_MAX_RETRIES = 10`）
- 仅当 `packageLabel` 抛 `"The next postings aren't ready"`（面单装配中，`awaiting_registration` 预期行为）时重试；`setTimeout` + `unref()`，不阻塞进程退出。
- 其他错误（含 `INVALID_ARGUMENT` 状态不允许）视为"放弃"，记录日志后结束，不再重试。

### 3.3 提前终止

- 已存在条码（`lower_barcode IS NOT NULL`）→ 幂等完成；
- 店铺未配置 `sync_credentials.clientId` → 放弃；
- 重试次数耗尽 → 记录日志，删除状态，后续扫描打单时按需实时拉取兜底。

## 4. 缓存落点

| 存储 | key | 内容 | 后续消费 |
|---|---|---|---|
| `waybill-cache.js`（内存） | `storeId|postings按字典序.pdf` | 面单 PDF Buffer | 打印页直接命中，无需再调 `packageLabel` |
| `op_posting_barcode` 表 | `UNIQUE(store_id, posting_number)` | 解析出的条码（`lower_barcode`）| 扫描打单条码校验、补条码 |

> 打印时仍有 `missingBarcodePostings` 兜底：本地条码缺失时实时调 `packageLabel` 解析回填（`waybill-barcode.js` / `label-barcode-daos.js`）。预取只是把这段耗时提前，不改变兜底逻辑。

## 5. 顺带修复：ship 路由 catch 块 ReferenceError（既有 bug）

- 旧代码：`const row = db.prepare(...).get(...)` 在 `try` 内声明，外层 `catch` 引用 `row?.postingNumber`。当异常发生在 `const row` 声明**之前**（如参数校验前抛错），catch 中 `row` 未定义 → `ReferenceError: row is not defined`（pm2 旧进程日志实锤，堆栈行号指向 catch 内 `row?.postingNumber`）。
- 修复：`let row = null;` 提升到 `try` 外，catch 中 `row?.postingNumber` 天然安全（null 可选链返回 undefined）。
- 注意：该错误发生在旧进程（pid 1586），本次预取改动只是让行号偏移，并非引入者。
