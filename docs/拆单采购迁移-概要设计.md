# Ozon 拆单采购关联迁移 · 概要设计

> 2026-09-18 · 状态:待确认决策点后实施

## 1. 背景与问题

Ozon FBS 拆单:母件数量减少(如 2→1),同时新增子件货件(`parent_posting_number` 指向母件)。

实例:`39133830-0717-1`、`39133830-0717-3` 原各 2 件 → 拆出子件 `-7`、`-5`,母件数量变 1。

**当前系统的行为**(代码现状):
- 同步只 upsert 货件与产品行数量(`syncOrderItems` 直接覆盖 quantity),子件作为全新订单+包裹落库
- 已关联的采购(`op_purchase_link`)全部留在母件 → **母件"多采"、子件"缺采"**:
  - 采购状态失真:子件显示未采购、母件虚高
  - 利润失真:母件背了 2 件的采购钱(利润偏低),子件 0 采购(利润虚高)
  - 需人工在采购弹窗重新分摊(本次实例即手工处理:1 个 1688 采购单手工拆成 5 个包裹级关联)

**附带发现的存量问题**:`recomputeAggregates` 只按**行级**关联(`ozon_order_item_id` 非空)重算 item 的已采数量/采购金额;包裹级关联不参与 → 实例中 `39133830-0717-2` 关联了采购但 item 已采显示 0。

## 2. 目标

拆单发生时,自动把母件采购关联按数量迁移到子件:
- 总数量、总金额守恒(金额分摊到分,余数归母件)
- 迁移后母/子包裹的采购状态、item 已采、利润全部正确
- 幂等可重入;不满足安全条件时不动数据、留提示转人工
- 全程留痕可审计

## 3. 触发时机

统一在订单同步落库路径(order-sync 的 upsert 批次末尾)执行 `reconcileSplitPurchases(storeId, touchedPostings)`:

- **触发 A**:本次 upsert 出现带 `parent_posting_number` 的子件(新子件到了)
- **触发 B**:本次 upsert 使某 item 的 quantity 减少(母件缩量了)

任一命中 → 对涉及的母件跑一次对账。fast/mid/slow/webhook 共用 upsert 路径,天然全覆盖。

## 4. 迁移算法(以母件为单位)

对每个子件 × 每个共同 SKU:

1. `movable` = 母件该 SKU 的关联数量合计 − 母件该 SKU 的 item.quantity(当前需求)
2. `deficit` = 子件该 SKU 的 item.quantity − 子件该 SKU 的关联数量合计
3. `k = min(movable, deficit)`;k ≤ 0 跳过(子件已采足或母件无富余)
4. 从母件关联行(FIFO,按 link.id 升序)逐行拆出:
   - `amount = round(原行.allocated_amount × k ÷ 原行.quantity, 2)`,分摊余数留在母件行
   - 新建子件**行级**关联:`(purchase_order_id, 子件package_id, 子件item_id, amount, k, alloc_mode=原行)`
   - 母件行 `quantity −= k`、`allocated_amount −= amount`;quantity 归 0 则删除该行
5. 母件的**包裹级**关联:若母件是单一 SKU 包裹,迁移时顺带升级为行级(修正 §1 的已采不计数问题);多 SKU + 包裹级 → 不自动(见 §5)
6. 复用 `recomputeAggregates` 重算母件包、子件包的聚合(total_purchase_amount / purchase_status / item 已采与金额)

## 5. 安全边界(不自动,转人工提示)

| 场景 | 处理 |
|---|---|
| 多 SKU 母件存在包裹级关联(无法判定归属哪个 SKU) | 跳过自动,子件 note 追加「拆单采购需人工迁移」 |
| 子件已有足额关联(用户已手工处理) | deficit=0 自然跳过,不重复 |
| 母件 is_ignored(搁置) | 跳过 |
| 已发货/已妥投的包裹 | 照常迁移(钱随货走,修正历史利润口径) |
| 金额精度 | 2 位小数,余数归母件 |
| 幂等 | movable/deficit 收敛为 0,重复执行无副作用 |

## 6. 留痕与展示

- **操作日志**:每次迁移写 audit 明细(母件号、子件号、采购单号、迁移数量、迁移金额)
- **订单处理列表**:货件号旁徽标「母件」/「子件」(子件悬浮显示母件号)——`parent_posting_number` 后端已透出,补前端展示
- 采购弹窗无需变化(迁移后按正常关联显示)

## 7. 决策点

1. **迁移方式**:A 全自动(§5 边界内自动迁,边界外提示)/ B 只提示不自动 / C 自动+失败转提示
   → 倾向 A:算法确定性高(同 SKU 数量对数量),金额守恒可审计
2. **包裹级→行级升级**:单一 SKU 包裹的包裹级关联在迁移时顺带升级为行级(修正 -2 那类已采=0 的显示)是否可接受
   → 倾向接受;不做全库批量升级,只在触碰到的包裹上顺带修
3. **手动兜底**:是否另加一个「拆单对账」手动入口(重跑 reconcile,运维/补历史用)
   → 倾向加(复用同一函数,挂在同步相关操作旁)
4. **徽标展示**:母件/子件徽标是否要做
   → 倾向做(纯展示,成本低,排查拆单问题直观)

## 8. 实施拆分

- **P1 DAO 核心**:`reconcileSplitPurchases`(算法+安全边界+recompute 复用),order-daos 或新 split-reconcile-dao
- **P2 触发接入**:order-sync upsert 批次末尾调用(A/B 双触发)
- **P3 展示与留痕**:列表徽标、note 提示、audit 日志
- **P4 验证**:用本次 39133830-0717-* 场景回放验证(先备份)、幂等重跑、多 SKU 包裹级跳过路径

## 9. 风险与边界

- 拆单与同步并发:reconcile 在同一同步事务序列内执行,无并发窗口
- 子件先于母件缩量到达(顺序颠倒):触发 B 在母件缩量时补跑,两触发互补
- Ozon 理论上可能合并回母件(未观察到):不做处理,数量回增时 movable 为负自然跳过
- 妙手侧包裹镜像:采购关联只在本系统 op_package 上,妙手侧无需改动
