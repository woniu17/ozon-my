# 跨店大包已发出识别与体现 — 功能设计

## 1. 背景

**真实案例**：发运单 `125108565`（yql02 大包）在 2026-11-01 通过跨店混装（`source='manual'`）带走了 7 个 yql04 店铺的订单，确认发运时这 7 个订单的 `op_package` 已被推进为 `dispatching`（交运中），`dispatched_at = 2026-11-01T07:45:37Z`。

但 **Ozon 平台不认跨店混装**：这 7 个订单在 Ozon 侧状态仍是 `awaiting_deliver`。Ozon 发运单创建流程无法添加跨店包裹，因此我们采用**折中处理**：把这 7 个订单再次纳入 yql04 自己的新发运单（如 `125173500`，`source='ozon'`）并走发运流程，从而在 Ozon 后台把这些订单标记为"已发运"，完成发货闭环。

**关键语义**（区别于普通重复发货）：
- 货件**物理上已随 125108565 大包发出**（集运仓已接收/签收）；
- 把它加入新发运单（125173500）**不是重复发货**，而是 **Ozon 侧补登记发运**；
- ERP 需要体现"已随大包发出"的事实，同时**允许并支持**用户在创建新发运单时再次加入这些货件做 Ozon 闭环。

## 2. 目标

1. 建立 **"已随跨店大包发出"** 的识别与标注机制，贯穿：
   - 发运管理（发运单货件列表）
   - 订单处理列表
   - 待发运候选 / 跨店混装候选（**标注而非拦截**，方便用户做 Ozon 补登记）
2. **不修改** Ozon 同步的状态字段（`op_ozon_order.status`、`op_package.is_shipped` 等），不污染数据；以 **UI 标注 + 流程提示** 为主。
3. 历史数据自动生效（125108565 已完结，方案上线即识别）。

## 3. 核心识别规则（纯派生，不新增表字段）

**定义**：货件"已随跨店大包发出" ⟺ 存在 `op_carriage_posting` 行满足：

```sql
cp.source = 'manual'              -- 跨店混装行
AND cp.removed_at IS NULL         -- 仍在该大包记录中（保留历史展示）
AND EXISTS (
  SELECT 1 FROM op_carriage_history ch
  WHERE ch.store_id = cp.store_id
    AND ch.carriage_id = cp.carriage_id
    AND ch.status IN ('received', 'delivered', 'closed')
)
```

**状态集合说明**（2026-11-07 与业务确认）：
- `received`：Ozon 已接收大包 → 已发出；
- `delivered`：已送达 → 已发出；
- `closed`：已完结，集运仓已签收大包 → 已发出；
- `cancelled`：**手动取消，大包没有发出** → 不视为已发出。

**其它要点**：
- 货件同时命中多个大包时，取**最近完成**的一个（按 `cp.added_at DESC`）。
- 该规则完全由现有表派生：`op_carriage_posting` 提供跨店行，`op_carriage_history` 提供发运单状态（定时同步已维护）。**无需迁移表结构**。

## 4. 各层改动

### 4.1 后端

#### 4.1.1 新增派生函数（复用 `attachCarriageOglTracking` 模式）

`order-daos.js` 新增 `attachCrossStoreShippedFlags(pkgRows)`：

- 输入：包裹行数组（含 `storeId`、`postingNumber`、`id`）。
- 查询：
  ```sql
  SELECT cp.store_id || '|' || cp.posting_number AS pkey,
         cp.carriage_id AS carriageId,
         ch.status,
         ch.tracking_number AS tracking,
         cp.added_at
  FROM op_carriage_posting cp
  JOIN op_carriage_history ch
    ON ch.store_id = cp.store_id AND ch.carriage_id = cp.carriage_id
  WHERE cp.source = 'manual'
    AND cp.removed_at IS NULL
    AND ch.status IN ('received', 'delivered', 'closed')
    AND (cp.store_id || '|' || cp.posting_number) IN (...)
  ORDER BY cp.added_at DESC
  ```
- 输出：`p.crossStoreShipped = { carriageId, status, trackingNumber, addedAt } | null`。
- 在 `listPackages` 中与 `attachCarriageOglTracking` 并列调用。

#### 4.1.2 发运单货件列表（`carriage/posting-list`）

在合并 `manualPostings` 之后，对每个货件计算 `cross_store_shipped`：

- **ozon 行**（如 125173500 里的 7 单）：按 `store_id + posting_number` 查是否命中识别规则 → 返回 `cross_store_shipped = { carriageId: 125108565, status, trackingNumber, addedAt }`。
- **manual 行**（如 125108565 里的 7 单）：当前发运单状态为 `received/delivered/closed` 时 → 返回 `shipped_with_this_carriage = true`。

#### 4.1.3 候选列表（**标注，不排除**）

| 接口 | 改动 |
|---|---|
| `carriage/mixed-candidates` | 返回结果附加 `cross_store_shipped` 标注（用户需据此识别"已随大包发出、待 Ozon 补登记"的货件，**不能排除**） |
| `carriage/available-postings` | 同上 |
| `carriage/pending-postings` | 同上 |

**注意**：不要用 `NOT EXISTS` 排除这些货件——把它们加入新发运单正是 Ozon 闭环的折中手段。

#### 4.1.4 `carriage/mixed/add` 与 `set-postings`

- **不拦截**已随大包发出的货件。
- 若某货件已随大包发出，返回结果中附加 `crossStoreShipped` 信息，供前端提示"已随大包发出，将用于 Ozon 补登记"。

### 4.2 前端

#### 4.2.1 `CarriageManage.vue` 货件列表

- 当前发运单已完成（`received/delivered/closed`）且 `p.source === 'manual'` → 行内绿色标签 **`✅ 已随本发运单发出`**。
- `p.cross_store_shipped` 非空（ozon 行）→ **信息色标签**（非警告）：**`📦 已随 125108565 大包发出（Ozon 补登记）`**，悬浮显示来源发运单状态/OGL 单号，点击可跳转 125108565 详情。

#### 4.2.2 `OrderProcess.vue` 订单列表

- `pkg.crossStoreShipped` 非空 → 状态列显示**信息色标签** **`已随 125108565 大包发出`**（悬浮显示"Ozon 补登记发运中"）。
- **倒计时调整**：`countdown`/`最迟发货` 的显示条件增加 `!pkg.crossStoreShipped` —— 已随大包发出的订单不再显示"最迟/剩发/已超时"（实际已交运）。
- OGL 徽标旁可加小字"跨店大包"。

### 4.3 安卓（二期，可选）

- 扫描发货/入库：扫到已随大包发出的订单时，提示"该订单已随 125108565 跨店大包发出，当前操作用于 Ozon 补登记"。
- 前置：扫描搜索接口返回 `crossStoreShipped` 标记。

## 5. 数据与兼容

- **无表结构变更**，纯派生查询。
- 历史数据自动生效：125108565 已完成（`received` → 后续 `closed`），其 7 个 manual 行自动标记"已发出"；125173500 中 7 个 ozon 行自动标注"已随大包发出（Ozon 补登记）"。
- 发运单归档后仍生效：`op_carriage_history.status` 保留 `received/delivered/closed`，识别继续成立。
- 125108565 的货件历史快照（`postings_json`）已含跨店行，无需回填。

## 6. 验收标准

1. 打开发运单 `125173500` 详情：7 个货件显示信息标签"已随 125108565 大包发出（Ozon 补登记）"。
2. 打开发运单 `125108565` 详情：7 个跨店货件显示"已随本发运单发出"。
3. 订单处理列表搜索这 7 个订单：显示"已随 125108565 大包发出"标签，且**不再显示发货倒计时**。
4. 跨店混装候选（`mixed-candidates`）中这 7 个订单**仍可出现**，但带"已随大包发出"标注，用户可据此识别并加入新发运单。
5. 扫描发货扫到这些订单有提示（二期）。

## 7. 边界与确认

| # | 问题 | 结论 |
|---|---|---|
| 1 | `closed` 是否视为已发出？ | **是**。已完结=集运仓已签收大包，确认已发出 |
| 2 | `cancelled` 是否视为已发出？ | **否**。手动取消=大包没有发出 |
| 3 | 已随大包发出的货件能否加入新发运单？ | **允许**，且候选列表必须保留它们——这是 Ozon 侧补登记发运的折中手段 |
| 4 | 纯派生 vs 冗余字段？ | 先纯派生（简单、无迁移）；若列表查询变慢，可在 `op_carriage_posting` 加 `shipped_at` 冗余字段并回填 |
| 5 | 标签语义 | 用**信息色/中性**标签（"已随大包发出（Ozon 补登记）"），**不用红色警告**，避免误导为重复发货 |

## 8. 实施记录（2026-11-07 已落地）

### 后端
- `order-daos.js`：新增 `attachCrossStoreShippedFlags(pkgRows)`，在 `listPackages` 中与 `attachCarriageOglTracking` 并列调用；订单列表返回 `pkg.crossStoreShipped`（驼峰，含 `carriageId/carriageStatus/trackingNumber/addedAt`）。
- `order-process.js`：新增 `attachCrossStoreShippedForPostings(postings, { currentStoreId, currentCarriageStatus, excludeCarriageId })`，应用于：
  - `carriage/posting-list`：发运单货件列表返回 `cross_store_shipped`（ozon 行，排除当前发运单自身）与 `shipped_with_this_carriage`（manual 行，当前发运单已完成时）；
  - `carriage/pending-postings`、`carriage/available-postings`、`carriage/mixed-candidates`：候选返回 `cross_store_shipped` 标注（不排除）；
  - `carriage/mixed/add`：返回 `added[].crossStoreShipped`。
- 关键实现细节：`op_carriage_history` 与 `op_carriage_posting` **仅按 `carriage_id` join**（发运单归属店铺与跨店货件店铺不同）；`added_at` 需用 `r.added_at` 访问（SQL 未加别名）。

### 前端
- `CarriageManage.vue`：货件列表（详情 + 创建发运弹窗）显示标签：
  - `shipped_with_this_carriage` → `✅ 已随本发运单发出`；
  - `cross_store_shipped` → `📦 已随 {carriageId} 大包发出（Ozon 补登记）`（悬浮显示来源发运单/状态/OGL 单号/加入时间）。
- `OrderProcess.vue`：状态列显示 `已随 {carriageId} 大包发出` 标签；最迟/剩发/已超时倒计时对 `crossStoreShipped` 订单隐藏。

### 验证结果（实际数据）
- `125173500`（yql04，formed）：35 货件中 7 个 ozon 行带 `cross_store_shipped → 125108565`。
- `125108565`（yql02，received）：36 货件中 24 个 manual 行带 `shipped_with_this_carriage`，自身 `cross_store_shipped = 0`。
- `pending-postings`（yql04）：12 个待发运货件中 7 个带 `cross_store_shipped → 125108565`。
- `mixed-candidates`：已随大包发出的 7 单被现有 `NOT EXISTS` 逻辑排除（不会再混装进其它大包），符合预期。
