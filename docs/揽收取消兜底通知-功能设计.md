# 揽收与取消兜底通知 — 功能设计

> 版本:v1.1(2026-09-13,M0 实测完成,已实施;**取消兜底启用方案 C**)
> 模块:ozon-webhook(unfulfilled-poller 扩展 + cancel-scanner 新增)
> 前置:[ozon-webhook-service-design.md](design/ozon-webhook-service-design.md)(服务设计)、[Ozon 推送通知 API](ozon-api/16-推送通知.md)(状态映射附录)
> 关联决策(2026-09-13 用户确认):
> ① 落地范围 = 揽收兜底 + 货件取消兜底;普通状态变更(TYPE_STATE_CHANGED 其余状态)**不做通知兜底**,仅静默校准 DB;
> ② 复用 unfulfilled-poller 现有轮询数据,不新增列表 API 调用——**❌ M0 实测推翻:cancelled 货件不出现在 unfulfilled list(4 店 12 单 0/12 在列),取消兜底已启用方案 C(§6)**。

***

## 1. 背景与目标

新订单通知已有兜底(unfulfilled-poller 每 2 分钟轮询 `/v4/posting/fbs/unfulfilled/list`,发现漏推货件 → 推飞书带 `(兜底通知)` 标注)。但其余飞书通知在 webhook 推送丢失/延迟时**无任何补偿**:

| 通知 | 消息类型 | 飞书机器人 | 兜底现状 |
| --- | --- | --- | --- |
| 新订单 | TYPE_NEW_POSTING | 独立(new) | ✅ 已有 |
| 货件取消 | TYPE_POSTING_CANCELLED | 独立(cancel) | ❌ 无 |
| 揽收 | TYPE_STATE_CHANGED + `posting_on_way_to_city` | 独立(pickup) | ❌ 无 |
| 普通状态变更 | TYPE_STATE_CHANGED(其余) | default | ❌ 无(本设计不做通知,仅校准) |

**目标**:参考新订单兜底模式,为**揽收**和**货件取消**补齐兜底通知——webhook 漏推时最多延迟 2 分钟由 poller 补发;同时顺带修正 DB 状态漂移和揽收统计漏计问题。

***

## 2. 现状调研结论

### 2.1 核心发现:unfulfilled list 数据被浪费

`unfulfilled-poller.js` 每轮(2 分钟)已拉取全店未妥投货件(±14 天 cutoff 窗口),每条 posting 含 `status` 与 `cancellation` 对象,但**当前只用于发现新货件**,状态信息直接丢弃。

Swagger 证据(`posting.v4.PostingFbsUnfulfilledListResponse.Postings`):

1. **`status` 枚举含 `cancelled` / `cancelled_from_split_pending`** —— 已取消货件(至少在窗口期内)仍出现在 unfulfilled 列表中 → **取消兜底可零额外 API 调用**;**❌ M0 实测推翻(2026-09-13):4 店 12 单已取消货件 0/12 出现在 unfulfilled list,取消兜底改走方案 C(§6)**;
2. **每条 posting 带 `cancellation` 对象**:`cancel_reason`(原因文本)、`cancel_reason_id`、`cancellation_initiator`(Seller/Client/Customer/Ozon/System/Delivery)、`cancellation_type`、`cancelled_after_ship` —— 取消兜底通知可携带比实时推送(`reason.message`)**更丰富**的取消详情;
3. **`delivering` 在 unfulfilled 返回枚举中**(未妥投全集含运输中) —— 揽收兜底可从状态对比得出。

### 2.2 状态词汇表:两套模型必须映射

DB `ozon_postings.status` 存**推送模型**状态(`posting_on_way_to_city` 等,由 webhook handler 写入),而 OPI 返回 **Seller API 模型**状态(`delivering` 等)。两套词汇**不同名**,必须映射(映射表见 16-推送通知.md 附录):

| Seller API 状态 | 推送模型状态 | rank | 说明 |
| --- | --- | --- | --- |
| `awaiting_verification` / `awaiting_approve` / `awaiting_packaging` / `awaiting registration` | `posting_created` | 0 | 已创建 |
| `acceptance_in_progress` | `posting_acceptance_in_progress` | 0 | 验收中 |
| `awaiting_deliver` | `posting_transferring_to_delivery` | 1 | 等待装运 |
| `delivering` | `posting_on_way_to_city` | **2** | **揽收级** |
| `arbitration` / `client_arbitration` | `posting_in_arbitration` / `posting_in_client_arbitration` | 2 | 仲裁(与运输同级) |
| `driver_pickup` | `posting_driver_pick_up` | 3 | 揽收级(司机取件) |
| `not_accepted` | `posting_not_in_sort_center` | 吸收 | 终态,按取消语义处理 |
| `cancelled` / `cancelled_from_split_pending` | `posting_canceled` | 吸收 | 终态 |

> `delivered` 不在 unfulfilled 响应枚举中(妥投即离开未妥投列表),本设计无需处理。

### 2.3 现有揽收统计的已知缺陷(顺手修复)

`buildTodayPickupSummaryFromDb` 按 `status='posting_on_way_to_city' AND last_received_at 当日` 计数:货件后续状态变更会**覆盖** status 与 last_received_at,导致当日揽收**漏计**(代码注释已自认此缺陷)。本设计引入 `pickup_at` 列(首次达到揽收级的时间戳)作为统计基准,一次修复。

***

## 3. 总体方案

扩展 `unfulfilled-poller.js` 的 `tick()`,从"单一发现新货件"升级为**四阶段状态机对比**,零新增列表调用:

```
tick()(每 2 分钟,每店铺)
  │
  ├─ 拉取 unfulfilled list(±14d cutoff 窗口,现有逻辑不动)
  │
  ├─ ① 新货件发现(现有)
  │     DB 无此 posting_number → 落库(状态取 API 实际状态映射值,
  │     不再固定写 posting_created)→ 新订单兜底通知
  │
  ├─ ② 状态对比(新增,内存完成)
  │     加载 DB 行 {status, pickup_at, cancel_reason_*} → Map
  │     对 list 中每条 posting:API status 映射为推送模型状态
  │       ├─ DB 已 cancelled → 跳过(终态吸收,天然幂等)
  │       ├─ 映射 rank > DB rank → UPDATE status(只前进不回退)
  │       └─ rank ≤ DB rank → 跳过(实时推送已领先)
  │
  ├─ ③ 揽收兜底(新增)
  │     API rank ≥ 2(delivering/driver_pickup) 且 pickup_at IS NULL
  │       → 置 pickup_at + 揽收兜底通知(带当日揽收统计)
  │     ※ 含场景①新货件发现时已在运送中:两通知都发,各自独立有意义
  │
  └─ ④ 取消兜底(M0 实测后移出本 poller:cancelled 货件不出现在 unfulfilled list,
        由独立 cancel-scanner(方案 C,§6)承担,幂等逻辑同 §4.4)
  │
  └─ 全部落库完成 → 查当日揽收统计 → 逐条发揽收兜底通知(批量内复用统计)
```

**幂等语义**(与新订单兜底一致):先落库后通知,通知失败仅记日志不重试;DB 状态/`pickup_at` 即去重标记,下轮不会重发。

## 4. 详细设计

### 4.1 Schema 变更(ozon_postings 加 2 列)

| 列 | 类型 | 用途 |
| --- | --- | --- |
| `pickup_at` | TEXT | 首次达到揽收级的时间戳;揽收通知去重标记 + 揽收统计新基准 |
| `cancel_initiator` | TEXT | 取消发起方(Seller/Client/Ozon/System/Delivery),取自 cancellation 对象 |

`schema.sql` CREATE TABLE 补列 + `db/index.js runMigrations` 补 ALTER(现有机制,照抄 `sale_amount_cny` 模式)。

**一次性回填**(runMigrations 内,幂等):`UPDATE ozon_postings SET pickup_at = last_received_at WHERE status='posting_on_way_to_city' AND pickup_at IS NULL` —— 存量揽收行用 last_received_at 近似,衔接新旧统计口径。

### 4.2 状态同步(阶段②)——只前进,不回退

```js
// rank 序:0(created/验收) < 1(待装运) < 2(揽收/仲裁) < 3(司机取件)
// cancelled / not_accepted:吸收态,任意 rank 可进入,进入后不退出
const API_TO_PUSH = { /* §2.2 映射表 */ };
const ABSORBING = new Set(['cancelled', 'cancelled_from_split_pending', 'not_accepted']);

function shouldAdvance(dbStatus, apiStatus) {
  if (isAbsorbing(dbStatus)) return false;              // DB 已终态 → 不动
  if (ABSORBING.has(apiStatus)) return true;            // API 终态 → 进入
  return rankOf(apiStatus) > rankOf(dbStatus);          // 只前进
}
```

未知 API 状态(映射表外)记 warn 日志跳过,不更新 DB(防脏写)。

### 4.3 揽收兜底(阶段③)

**触发条件**:`rankOf(apiStatus) >= 2`(delivering / driver_pickup) 且 DB 行 `pickup_at IS NULL`。

**动作**:置 `pickup_at = now`(ISO)→ 状态同步随 ② 一并 UPDATE → 通知(见 4.6)。

**跳级处理**:若货件从 awaiting_deliver 直达 driver_pickup,同样触发(揽收语义 = "已交给物流")。

**新货件特例**:阶段① 发现的新货件若 API 状态已是运送中,走 ① 新订单兜底 + ③ 揽收兜底各一条——订单创建与揽收是两个独立事件,分开发送。

### 4.4 取消兜底(阶段④)

**触发条件**:API status ∈ `{cancelled, cancelled_from_split_pending}` 且 DB 状态 ≠ `posting_canceled`。

**动作**:UPDATE `status='posting_canceled'`、`cancel_reason_id/cancel_reason_message`(取自 `cancellation.cancel_reason_id/cancel_reason`)、`cancel_initiator` → 通知(见 4.6)。

**幂等**:webhook 实时取消(handler)先 UPDATE 再通知,兜底只对 DB ≠ cancelled 的行触发,不会重发;反之兜底先处理、实时推送后到时 handler 的 UPDATE 幂等落库、通知照发(实时通知独立于兜底,同新订单语义——两类通知来源不同标注不同,重复概率低)。

### 4.5 webhook handler 侧配合改动

| 文件 | 改动 |
| --- | --- |
| `state-changed.js` | 落库时若 `rankOf(new_state) ≥ 揽收级` 且 `pickup_at IS NULL` → 一并置 `pickup_at`(去重标记,防 poller 重复推)。**通知触发同步放宽**:揽收通知从"精确 `posting_on_way_to_city`"放宽为"首次达到揽收级"(见 §5 决策点 D1) |
| `posting-cancelled.js` | 无需改动(status=cancelled 天然去重) |
| `new-posting.js` | **终态保护**:ON CONFLICT 的 status 改为 `COALESCE(原status, excluded.status)`,同号晚到的 NEW_POSTING(乱序重推)不把已推进/已取消状态回退为 `posting_created` |

### 4.6 通知格式(与实时推送一致 + 末行标注)

**揽收兜底**(→ `webhookUrlPickup`):

```
[揽收] [店铺名] [货件号]
货件号: ...
卖家: 店铺名(ID)
变更时间: <检测时间 now>
新状态: posting_on_way_to_city        ← 映射后的推送模型状态
—— 当日各店铺揽收统计(Asia/Shanghai)——
• 店铺A: 揽收  3 单
合计:揽收  3 单
(兜底通知)
```

**取消兜底**(→ `webhookUrlCancel`):

```
[货件取消]
货件号: ...
卖家: 店铺名(ID)
取消时间: <检测时间 now>
旧状态: <DB 更新前状态>
取消原因: <cancellation.cancel_reason>
取消发起方: <cancellation.cancellation_initiator>   ← 比实时推送多出的信息
(兜底通知)
```

> 标题规则遵循项目记忆:不带 `[兜底]` 前缀,末行 `(兜底通知)` 标注。取消兜底标题去掉"Ozon 推送"字样(来源不是推送,避免误导),实时标题不动。

**统计复用**:一轮内全部 DB 更新完成后调一次 `buildTodayPickupSummaryFromDb()`(改用 pickup_at 口径),循环内复用文本块——与现有新订单兜底的 `buildTodaySummaryFromDb` 模式一致。

### 4.7 揽收统计口径切换

`buildTodayPickupSummaryFromDb` 查询改为:

```sql
SELECT seller_id, COUNT(*) AS pickup_count
FROM ozon_postings
WHERE pickup_at IS NOT NULL AND pickup_at >= ? AND pickup_at < ?   -- 当日 UTC 范围
GROUP BY seller_id
```

修复现状漏计(后续状态变更覆盖 status 导致漏统计);回填保证存量衔接。

## 5. 边界情况与决策点

| # | 场景 | 处理 |
| --- | --- | --- |
| E1 | 消失货件(list 中不见,DB 仍非终态) | **不主动单查**。妥投即离开列表是正常路径,逐条 `/v3/get` 单查成本高。取消若真的"取消后从列表消失",由备选方案 C 兜住(§6) |
| E2 | Ozon 重试导致推送乱序(后状态先到) | rank 只前进 + pickup_at 首次置位,天然免疫乱序 |
| E3 | 服务重启(pmem 丢失内存态) | 全部去重标记在 DB(pickup_at/status),重启安全 |
| E4 | 翻页中途失败(现有 partial 语义) | 已拉到的部分照常走四阶段;未拉到的下一轮补 |
| E5 | 质检单(02131/024785 开头) | 揽收/取消兜底**照常通知**(运营需跟踪质检单流转),仅标题不带 `[质检]`(与实时揽收一致) |
| E6 | `cancelled_after_ship=true`(交运后取消) | 正常走取消兜底;此场景对利润口径有影响(订单处理页已按取消口径处理,本设计不涉及) |

**决策点(需确认)**:

- **D1 揽收通知触发放宽**:webhook 实时揽收通知从"精确 `posting_on_way_to_city`"放宽为"首次达到揽收级(≥ delivering rank)"。影响:跳级推送(如直接 `posting_in_courier_service`)从"普通状态变更通知(default 机器人)"改走"揽收通知(pickup 机器人+统计)"。**理由**:跳级时货件确已揽收,走揽收通知语义更准;且与 pickup_at 置位逻辑对齐,避免"置了标记但没通知"的漏报窗口。若不接受,则 pickup_at 仅在精确匹配时置位,跳级场景交由兜底补发(延迟 2 分钟)。
- **D2 取消兜底标题**:建议 `[货件取消]`(去掉"Ozon 推送"),见 §4.6。

## 6. 方案 C:独立取消扫描器(M0 实测失败,已启用 ✅)

**M0 实测结论(2026-09-13)**:已取消货件不出现在 unfulfilled 列表(4 店 12 单 0/12 在列),主路径取消兜底不可行;`/v4/posting/fbs/list` + `statuses=['cancelled']` 可精确拉取已取消货件(含完整 `cancellation` 对象),`last_changed_status_date` 增量过滤生效。已落地为 `src/services/cancel-scanner.js`:

```
每 10 分钟(取消时效性要求低于新订单),每店铺:
POST /v4/posting/fbs/list
  filter: {
    since: now-30d, to: now,                    // 必填,按 in_process_at
    statuses: ['cancelled'],                     // M0 实测确认支持
    last_changed_status_date: { from: lastScanAt } // 增量:仅状态近期变化的
  }
→ 与 DB 对比(同 §4.4 幂等逻辑)→ 取消兜底通知
```

- 扫描游标存内存,启动时回退 2h 窗口重扫(DB 幂等保证不重发);
- 实现补充:tick 全部店铺成功后游标推进到 tick 开始时刻(窗口无缝);任一店铺失败保留旧游标下轮重扫(幂等);
- DB 无行的取消单(连 NEW_POSTING 都漏推)插入最小记录并发取消通知(不发新订单通知——已取消订单对运营无新订单意义);UPDATE 带非取消守卫,与实时取消推送并发到达时不双重通知;
- API 消耗:每店每 10 分钟 1 次列表调用(通常 0 页数据),可接受。
