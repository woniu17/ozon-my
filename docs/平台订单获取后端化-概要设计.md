# 平台订单获取后端化 — 概要设计文档

> 版本：v1.0
> 日期：2026-09-12
> 模块：erp-backend-lite/src/services/platform-orders/（新增）
> 涉及前端：web/src/views/OrderProcess.vue（采购弹框 + 补全采购信息）
> 语义基准：miaoshou-helper/background.js、miaoshou-helper/ali-1688-page-bridge.js（插件三平台订单代理）
> 参考实现：qxqx/shallow-collect.js（cloakbrowser PID 锁范式）、qxqx/persistent.js（.linqx-profile 维护）

---

## 1. 背景与目标

### 1.1 现状问题

订单处理页面的采购弹框目前通过 miaoshou-helper 扩展协作获取 1688 / 淘宝 / 拼多多订单：

- 链路长且脆弱：前端 `postMessage` → erp-bridge.js 中继 → background.js →（1688 还需
  content script 页面桥接）→ 原样回传，任一环节失效都要人工排查
- 强依赖用户日常 Chrome：扩展必须启用、平台页必须登录在**用户浏览器**里，
  ERP 页面与扩展版本耦合（扩展改动需 chrome://extensions 重载 + 刷新 ERP 页）
- 1688 依赖隐藏标签页存在（找不到需自动开 tab 并盲等 8s），首拉体验差
- 妙手订单同步已迁 ERP 后端（/sync-from-miaoshou），三平台订单是插件协作的最后残留

### 1.2 设计目标

把三平台订单获取整体迁入 ERP 后端，后端使用 cloakbrowser（`.linqx-profile`）在页面
上下文执行请求：

1. **语义对齐**：请求参数、签名、响应标准化与插件实现逐字段一致（`{ok, orders|result|error}`
   结构），前端 `applyPddSelection` 等导入逻辑零改动
2. **解耦前端与扩展**：前端从 postMessage 桥改为 HTTP 调后端；平台登录态集中于
   `.linqx-profile`，与用户日常浏览器彻底分离
3. **无人值守基础**：后端持有浏览器会话后，后续可扩展批量/定时补全（本次不做）
4. **登录态维护零新增**：复用 qxqx 已有 `persistent.js` 手动登录，后端与其 PID 锁互斥

### 1.3 非目标

- 妙手订单同步（MS_* 链路）不在本次范围
- 订单数据落库路径不变（仍为前端透传，入库走现有 submitPurchase / 补全接口）
- 不做后端批量补全任务化（串行限速逻辑留在前端，仅替换调用方式）
- 不采集订单之外的平台数据（商品详情、物流轨迹等不在范围）

## 2. 现状基准（插件链路语义）

### 2.1 三平台接口特性（2026-08/09 实测注释，background.js 头部）

| 平台 | 接口 | 签名/依赖 | 上下文要求 |
|---|---|---|---|
| 拼多多 | `mobile.yangkeduo.com/proxy/api/api/aristotle/order_list_v4`（列表）`order_list_search_v4`（搜索） | 仅浏览器登录 Cookie（credentials include），无需 anti_content；`pdduid` 从 `pdd_user_uid` cookie 兜底 | 无 referer/origin 要求（SW 裸 fetch 已可行） |
| 1688 | `h5api.m.1688.com/h5/mtop.1688.trading.dataline.service/1.0/`，serviceId=`OrderListDataLineService.buyerOrderList` | mtop 签名 `sign=md5(token&t&appKey&data)`，token 取 `_m_h5_tk` cookie 下划线前段，appKey=12574478 | **必须**在 `air.1688.com` 页面上下文 fetch（referer/origin 过 baxia 风控） |
| 淘宝 | `h5api.m.taobao.com/h5/mtop.taobao.order.queryboughtlistV2/1.0/` | 同一套 mtop 签名（appKey 同 12574478，`_m_h5_tk` 域独立） | query 必须带 `ttid=1@tbwang_windows_1.0.0#pc` + `needLogin=true`，缺 ttid 报服务内部故障 |

通用机制：

- mtop token 失败（`FAIL_SYS_TOKEN_EMPTY` / `FAIL_SYS_ILLEGAL_ACCESS`）→ 服务器轮换
  `_m_h5_tk` cookie → 重取重签重试 1 次
- 金额单位分转元；淘宝响应为卡片化组件（shopInfo_/orderItemInfo_/orderPayment_/orderStatus_
  前缀）需聚合还原
- 搜索接口与列表接口同 API，仅 param/data 差异（1688 加 `word`；淘宝 OrderType 改
  `OrderSearch` + condition 加四个 word 字段；拼多多 type=search 三件套）

### 2.2 可行性结论

**可行**，风险集中在登录态维护，不在技术打通：

- 拼多多/淘宝：SW 裸 fetch（无 referer、无浏览器 TLS 指纹）已实测可行 → 换 cloakbrowser
  页面上下文 fetch 是**能力超集**（真实指纹 + 自动 cookie/referer），只会更稳
- 1688：唯一硬约束"页面上下文 fetch"正是 ali-1688-page-bridge.js 存在的理由；cloakbrowser
  导航同一订单页 URL 后 `page.evaluate` **机制完全等价**（指纹更真实）
- 登录态：mtop token 与订单会话全在浏览器 profile 里，`launchPersistentContext(.linqx-profile)`
  与扩展 `chrome.cookies` 读的是同一形态的持久化存储；签名/normalize 为纯 JS 可整体移植
- 工程：qxqx 已在同机 Windows + Node 验证 cloakbrowser 0.5.9（Playwright API）；erp-backend-lite
  Node ≥22.5 满足 engines 要求；浏览器二进制已缓存 `~/.cloakbrowser/`

### 2.3 逐平台风险

| 平台 | 风险等级 | 说明 |
|---|---|---|
| 拼多多 | 低 | 接口不校验 referer/TLS，纯 Cookie 会话 |
| 淘宝 | 低-中 | mtop 签名 + Cookie 已实测；ttid 查询参数必须保留 |
| 1688 | 中 | baxia 对上下文敏感，但页面上下文 fetch 正是现方案机制，属等价迁移；新增风险仅 headless 指纹（cloakbrowser 71 项 C++ 补丁覆盖）与偶发滑块（透传错误人工处理） |

## 3. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ OrderProcess.vue（采购弹框 · 补全采购信息）                    │
│   HTTP 替代 postMessage 桥（erp-pdd / erp-ali / erp-tb 下线） │
└──────────────────────────┬───────────────────────────────────┘
                           │ GET /admin/api/platform-orders/*
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ erp-backend-lite（pm2）· platform-orders 服务（新增）          │
│  ┌────────────┐   ┌──────────────┐   ┌────────────────────┐  │
│  │ 路由+请求队列 │ → │ 平台适配器 ×3 │ → │ 浏览器管理器        │  │
│  │ 互斥串行     │   │ pdd/1688/tb  │   │ 懒启动·PID锁·回收  │  │
│  │ 错误码映射   │   │ list+search  │   │ 崩溃自动重建       │  │
│  └────────────┘   └──────────────┘   └─────────┬──────────┘  │
└───────────────────────────────────────────────┼──────────────┘
                                                │ page.evaluate（单参数）
                                                ▼
┌──────────────────────────────────────────────────────────────┐
│ cloakbrowser launchPersistentContext（.linqx-profile）        │
│  逐平台导航订单页 → 页面上下文 fetch 签名请求 → normalize 回传  │
│  · air.1688.com 订单页（baxia 上下文要求）                      │
│  · h5api.m.taobao.com（mtop + ttid）                           │
│  · mobile.yangkeduo.com（Cookie 会话）                         │
└──────────────────────────────────────────────────────────────┘
        ▲ PID 锁互斥
        │ qxqx/persistent.js（手动登录 1688/淘宝/拼多多，可见窗口）
```

> 数据流向：前端 HTTP 调后端 → 后端经互斥队列串行驱动 cloakbrowser 页面上下文取数 →
> 标准化响应原样回传（结构与插件返回逐字段一致）。

### 3.1 核心决策（已确认）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 部署形态 | **内嵌懒启动** | 浏览器作为 erp-backend-lite 子进程，首个请求才启动，空闲 10 分钟自动回收；省内存，pm2 重启经退出钩子自动清理 |
| 登录维护 | **persistent.js 手动登录** | 复用 qxqx 现有脚本零新增代码；后端与其 PID 锁互斥；AUTH_REQUIRED 时前端提示登录 |
| 旧插件链路 | **验证稳定后删除** | M3 切换、稳定运行一段后清理前端桥代码与扩展三平台路由，保持代码干净 |
| 补全链路 | **前端逐单调后端** | 串行限速（2s/单、失败退避 5s、连败 3 次中止）逻辑留在前端，仅替换调用方式，行为与现在一致 |
| 响应契约 | **与插件逐字段对齐** | `{ok, orders|result|error}`，orderSn/statusPrompt/amount/goods[].thumbUrl 等字段不变，前端导入逻辑零改动 |
| 1688 执行位置 | **页面上下文 page.evaluate** | 等价 content script 机制（referer/origin 过 baxia），导航订单页 URL 与扩展自动开 tab 同款 |
| 并发模型 | 进程内互斥队列，单浏览器串行 | cloakbrowser 同一 userDataDir 不允许双开；订单弹框场景并发量极低，串行足够 |

### 3.2 与现有系统的共存关系

- `.linqx-profile` 与 persistent.js（手动登录）通过 PID 锁互斥；占用期间接口返回
  `PROFILE_LOCKED` 提示
- `.ozon-profile`（浅采/深采/价格监控）与 `.linqx-profile` 物理隔离，互不影响
- 妙手订单同步（MS_* 链路）不动；扩展其余功能（妙手提取等）不动
- ERP 鉴权沿用现有 authMiddleware（管理页 JWT）；新路由挂 /admin/api 下

## 4. 模块设计

```
src/services/platform-orders/
  browser-manager.js   # cloakbrowser 单例：懒启动 / 空闲回收 / PID 锁 / 崩溃重建
  mtop-sign.js         # MD5 签名 + mtop/淘宝参数构造（纯函数，可单测）
  queue.js             # 进程内互斥队列（单浏览器串行，先到先得）
  adapters/
    pdd.js             # order_list_v4 列表 + order_list_search_v4 搜索
    ali1688.js         # dataline mtop（页面上下文）+ token 轮换重试
    taobao.js          # queryboughtlistV2（卡片化聚合还原）+ 订单号搜索
src/routes/platform-orders.js   # 挂到 app.js，async handler
```

- 签名/normalize 逻辑从 background.js、ali-1688-page-bridge.js 移植；MD5 签名源码以
  字符串形式注入 evaluate 执行（对齐 qxqx "注入 lib 源码用 page.evaluate(源码)" 惯例）
- `page.evaluate` 单参数限制：payload 合并为单对象传入
- 新增依赖：`cloakbrowser` + `playwright-core`（peer dep）

## 5. 接口设计

| 接口 | 说明 |
|---|---|
| `GET /admin/api/platform-orders/:platform?tab=&size=` | platform = `pdd` / `ali1688` / `taobao`；返回 `ok({ orders })`，替代原 PDD/ALI/TB_GET_ORDERS |
| `GET /admin/api/platform-orders/:platform/search?orderSn=` | 返回 `ok({ result\|null })`，替代原三个 SEARCH_ORDER |
| `GET /admin/api/platform-orders/status` | 浏览器运行态（running/idle）+ 各平台登录态探测（附 cookieNames 诊断，仅名称不含值），替代原 PING/PONG 桥探测 |

- 响应采用后端统一 `ok()` 封装（`{ok:true, data:...}`，与其余 admin API 一致）；
  **orders/result 内部字段结构与插件返回逐字段一致**，前端 M3 只改调用方式
- 鉴权沿用现有 authMiddleware（管理页 JWT / 服务 `x-api-key`，curl 验证用后者）
- 超时：冷启动（launch + 导航）实测约 4-5s → 接口超时 60s 余量充足；热路径 <1s
- 错误码统一映射（前端按 code 出对应 toast）：

| 错误码 | 判定 | 前端提示 |
|---|---|---|
| `AUTH_REQUIRED`(403) | 平台 401/403 或 mtop 登录态错误 | "请运行 qxqx 的 persistent 登录 xx 平台" |
| `RISK_VALIDATE`(409) | `FAIL_SYS_USER_VALIDATE`（baxia/滑块） | "风控拦截，请在 persistent 窗口过验证后重试" |
| `PROFILE_LOCKED`(409) | .linqx-profile 被其它 Chromium 实例占用（persistent.js 窗口未关）或本服务 PID 锁冲突 | "profile 正在被 persistent.js 占用，请稍后" |
| `BROWSER_ERROR`(502) | 浏览器崩溃/启动失败/网络/风控异常 | 通用错误，下次请求自动重建浏览器 |
| `TIMEOUT`(408) | 任务超时（浏览器已自动回收） | "请求超时，请重试" |

## 6. 关键流程

```
① HTTP 请求到达 → 互斥队列排队（单浏览器串行，先到先得）
② 确保浏览器就绪
   PID 锁检查（被 persistent 占用 → PROFILE_LOCKED）
   未运行 → launchPersistentContext({ userDataDir, headless: true })（冷启动 ~15s）
   导航对应平台订单页（1688: air.1688.com/app/ctf-page/trade-order-list/buyer-order-list.html）
③ 页面上下文 fetch（page.evaluate 执行 mtop 签名请求，单参数对象）
   token 失败（FAIL_SYS_TOKEN_EMPTY/ILLEGAL_ACCESS）→ 重取 cookie 重签重试 ×1
   淘宝 query 必须带 ttid + needLogin=true
④ 标准化返回（normalize → {ok, orders}），错误按 §5 映射错误码
⑤ 空闲计时：10 分钟无请求 → ctx.close() 释放 profile + 删锁文件
```

生命周期：

- **懒启动**：首个请求触发；**崩溃重建**：browser disconnected → 下次请求自动重新 launch
- **pm2 restart erp**：进程退出钩子关闭浏览器 + 清锁文件；孤儿进程兜底靠 PID 锁检测
  （进程已死则覆盖锁，复用 shallow-collect.js acquireLock 模式）

## 7. 登录态与 Profile

- `.linqx-profile` 由用户手动维护：跑 qxqx 已有 `npm run persistent`（可见窗口）→
  登录 1688 / 淘宝 / 拼多多 → 关闭释放 profile（**零新增代码**）
- 1688 导航订单页本身会刷新 `_m_h5_tk` token，与扩展"找不到 tab 自动开隐藏页"机制等价
- 登录态探测（2026-09 实测 cookie 名，与插件侧文档注释有出入）：
  pdd → `PDDAccessToken`/`pdd_user_id`（实际无 `pdd_user_uid`，会话照样有效）；
  ali1688 → `_m_h5_tk`/`__cn_logon__`；taobao → `_m_h5_tk`/`tracknick`

## 10. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 1688 baxia 滑块 | 中 | 错误透传 `RISK_VALIDATE`；stealth + 登录态降低触发率；必要时切 headed 人工过验证 |
