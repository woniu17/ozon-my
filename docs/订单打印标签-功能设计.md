# 订单打印标签(Ozon面单打印) — 功能设计

> 版本:v1.0(2026-09-02)
> 模块:erp-backend-lite 订单处理(order-process)
> 前置调研:妙手ERP扫描发货页打印面单流程观察 + Ozon API `/v2/posting/fbs/package-label`

***

## 1. 背景与目标

当前 ERP 订单处理页的「打单交运」按钮(OrderProcess.vue wait\_ship 行操作)只做**本地状态标记**:
调用 `POST /admin/api/order-process/print-label` → `orderPackageDao.markWaybillPrinted()` 写 `waybill_printed_at` 并流转 `wait_ship → ship_success`。

真实面单打印仍在妙手ERP「扫描发货」页完成,两套系统来回切换。

**目标**:在 ERP 订单处理页直接调用 Ozon 官方 API 获取面单 PDF 并打印,打印完成后流转状态,实现"打单交运"闭环,摆脱对妙手的依赖。

***

## 2. 现状调研结论

### 2.1 妙手「打印面单」流程观察(2026-09-02 实测)

在妙手扫描发货页点击行内「打印面单」后,捕获到以下请求序列(全部 200):

| #   | 接口                                                                                           | 作用                          |
| --- | -------------------------------------------------------------------------------------------- | --------------------------- |
| 1   | `POST /api/order/package/createPrintDownloadPerformanceLog`                                  | 创建打印性能日志                    |
| 2   | `POST /api/platform/ozon/order/waybill/getOpOrderPackageIdAndLogisticsTemplateConfigInfoMap` | 获取 Ozon 面单模板配置(纸张规格等)       |
| 3   | `POST /api/order/waybill/getOpOrderPackageIdAndWaybillImageBase64ListMap`                    | **获取面单图片(base64)**,服务端生成/缓存 |
| 4-5 | `POST /api/order/package/updatePrintDownloadPerformanceLog` ×2                               | 更新性能日志                      |
| 6   | `POST /api/order/package/addOpOrderPackagesPrintLogs`                                        | 记录打印日志                      |

**关键观察**:

- 妙手服务端把面单转成 **base64 图片**,前端拿到后**静默发送到本地标签打印机**(HPRT D35BT),无弹窗、无预览。

- 面单数据由妙手服务端与 Ozon 之间完成拉取(推测内部即调 `/v2/posting/fbs/package-label`),前端不直连 Ozon。

- 行状态随之更新为「发货成功 + 已打印面单」。

**对我们的启示**:妙手的"图片+静默打印"依赖浏览器插件/打印控件,个人 ERP 不具备该环境;Ozon 原生返回的是 **PDF**,用浏览器标准打印能力(打开 PDF → Ctrl+P)即可,无需额外控件。

### 2.2 Ozon API:`POST /v2/posting/fbs/package-label`

依据 docs/ozon-api/05-FBS订单与配送.md:

- **请求体**:`{ "posting_number": ["28787928-0839-2", ...] }`(string 数组,**单次最多 20 个**)

- **响应**:含标签的 **PDF 文件(二进制流)**

- **约束**:

  - 只要有一个货件出错,**整批**都不会生成标签(全有或全无);

  - 建议在订单装配完成后 **45-60 秒**再请求;

  - 返回错误 `The next postings aren't ready` 表示标签未就绪,应稍后重试;

  - 认证走现有 OPI 封装(`Client-Id` / `Api-Key`)。

### 2.3 ERP 现有架构落点

| 层      | 文件                                            | 现状                                                                                                                  |
| ------ | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| OPI 服务 | `src/services/ozon-opi.js`                    | `call()` 统一封装认证/超时/错误,但**按 JSON 解析响应**,不支持二进制                                                                       |
| 后端路由   | `src/modules/order-process.js`                | 已有 `POST /print-label`(纯标记);`runSyncAllList` 展示了 store 解析模式(`config.loadStores()` + `sync_credentials.clientId` 过滤) |
| DAO    | `src/db/dao/sqlite/order-daos.js`             | `op_package` 含 `ozon_order_id`(=posting\_number)、`store_id`、`waybill_printed_at`、`operate_status`                   |
| 前端 API | `web/src/api/order-process.js` + `request.js` | 全 JSON 封装,**无 blob 响应处理**                                                                                           |
| 前端 UI  | `web/src/views/OrderProcess.vue`              | `wait_ship` 行有「打单交运」按钮(`onPrinted`)                                                                                 |

## 3. 总体方案

```
┌──────────────────────── ERP 前端(OrderProcess.vue)────────────────────────┐
│  行按钮「打印面单」(wait_ship)          工具栏「批量打印面单」(wait_ship tab) │
│        │ 按店铺分组,≤20/组                     │ 同左                        │
│        ▼                                        ▼                            │
│  fetch POST /admin/api/order-process/package-label  (responseType: blob)     │
└────────────────────────────────────┬───────────────────────────────────────┘
                                     ▼
┌──────────────────────── ERP 后端(order-process.js)────────────────────────┐
│  ① 校验 packageIds → 查 op_package(ozon_order_id + store_id)                 │
│  ② 本地文件缓存命中? ──命中──► 直接返回 PDF(不再打 Ozon)                   │
│        │ 未命中                                                              │
│  ③ 按 store 分组,每组调 ozonOpi.packageLabel(store, postingNumbers)         │
│     (callRaw 返回 Buffer + Content-Type 校验)                               │
│  ④ 写文件缓存 data/waybills/<store_id>__<posting_numbers>.pdf                │
│  ⑤ 响应 PDF 流(application/pdf)                                             │
└────────────────────────────────────┬───────────────────────────────────────┘
                                     ▼
                     浏览器新标签打开 PDF → 用户 Ctrl+P 打印
                                     ▼ (打印成功后前端调用,自动)
                 现有 POST /print-label → markWaybillPrinted → 流转 ship_success
```

**核心原则**:

1. **复用**现有状态流转(`markPrinted`/`markWaybillPrinted`)不动;
2. PDF 打印交给浏览器标准能力,**不引入**打印控件、不新增 pdf 合并依赖;
3. **文件缓存**面单(同一 posting\_number 的标签内容不变),降低 Ozon 调用频次与限流风险;
4. 跨店铺/超20单由**前端分组串行**处理,每组一个 PDF。

## 4. 详细设计

### 4.1 OPI 层:`ozon-opi.js` 新增二进制调用

现有 `call()` 会 `JSON.parse` 响应,PDF 会损坏。新增 `callRaw()`:

```js
// 二进制响应版 call:返回 { buffer, contentType }
// 供 /v2/posting/fbs/package-label(PDF)等非 JSON 接口使用
async function callRaw(store, path, body, { timeoutMs = DEFAULT_TIMEOUT_MS } = {}) {
  // 认证头/超时/错误映射与 call() 一致(抽公共 buildRequest)
  // 差异点:
  //   - res.body.arrayBuffer() 代替 .text()
  //   - 校验 Content-Type 含 application/pdf(防网关拦截返回 HTML 错误页)
  //   - 非 2xx 时仍读 text 转 JSON 取 message(保持错误语义)
}
```

新增导出方法:

```js
// /v2/posting/fbs/package-label — 打印标签
// postingNumbers: string[],单次 ≤20(调用方负责分组)
// 返回 { buffer: Uint8Array, contentType: string }
export function packageLabel(store, postingNumbers) {
  return callRaw(store, '/v2/posting/fbs/package-label', { posting_number: postingNumbers });
}
```

**错误语义**:

- HTTP 400 + message 含 `aren't ready` → 抛 `ApiError(LABEL_NOT_READY)`,前端提示"面单未就绪,请稍后重试"(装配后 45-60s);

- 其余沿用现有 `NETWORK_ERROR`/`TIMEOUT` 映射。

### 4.2 缓存设计(文件缓存)

- **位置**:`erp-backend-lite/data/waybills/`(gitignore,随 SQLite 数据同级);

- **命名**:`<store_id>__<posting_numbers 按字典序 join('-')>.pdf`(一组一个文件,天然支持单/批);

  - 单个打印时组内只有 1 个 posting\_number,即 `<store_id>__<posting_number>.pdf`;

- **策略**:

  - 命中缓存 → 直接读文件返回,**不调 Ozon**;

  - 缓存**不过期**(Ozon 同一货件的标签条码内容固定,重复打印场景如丢件补打必须返回同版面单);

  - 提供"强制刷新"参数 `?refresh=1` 忽略缓存重拉(异常兜底);

- **存储清理**:文件量级 ≈ 日订单量(百级/天),单文件几十 KB,无需清理任务;后续如需可在删除包裹时联动删文件(v1 不做)。

### 4.3 后端路由

```
POST /admin/api/order-process/package-label
```

**请求体**:

```json
{ "packageIds": [101, 102, 103], "refresh": false }
```

**约束与行为**:

- `packageIds` 非空,≤20(与 Ozon 单次上限对齐,超 20 返回 400);

- 查 `op_package` 得 `(ozon_order_id, store_id)` 列表:

  - 任一包裹不存在 → 400 列出缺失 id;

  - **必须同属一个 store\_id**(OPI 按店铺认证)→ 混店铺返回 400,提示前端分组;

- 缓存未命中:取该 store 的 credentials(`config.loadStores()` 过滤 `sync_credentials.clientId`),调 `packageLabel()`:

  - 成功 → 写缓存文件 + 返回 PDF;

  - `LABEL_NOT_READY` → 409 + 明确 message(前端识别重试);

- 响应头:`Content-Type: application/pdf`、`Content-Disposition: inline; filename="waybill-<n>单.pdf"`;

- 打印**不自动流转**状态(见 4.5 决策 D3:前端在打印动作完成后调用现有 `markPrinted`)。

**代码落点**:`src/modules/order-process.js` 新增路由(错误路径用 `ok()`/JSON envelope,成功路径直接 `res.end(buffer)`);缓存读写抽到 `src/services/waybill-cache.js`(≤40 行,含 `get()/set()` 与路径生成)。

### 4.4 前端设计

#### 4.4.1 API 层(`web/src/api/order-process.js`)

新增 blob 请求方法(`request.js` 增加通用 `postBlob`,复用 token 注入/401 处理,响应读 `blob()`,非 2xx 时尝试 `blob.text()` 解析 envelope message):

```js
// 获取面单 PDF(blob);packageIds ≤20 且须同店铺;refresh=true 忽略缓存
export function fetchPackageLabel(packageIds, refresh = false) {
  return request.postBlob('/admin/api/order-process/package-label', { packageIds, refresh });
}
```

#### 4.4.2 交互(`OrderProcess.vue`)

**A. 行级按钮(单包裹打印)**

`wait_ship` 行操作区,原「打单交运」按钮拆为两个:

```
[打印面单]  ← 新增,主按钮:拉 PDF → 新标签打开 → 确认后流转
[仅标记交运] ← 原 onPrinted 逻辑降级为兜底(ghost 小按钮)
```

`onPrintLabel(pkg)` 流程:

```
点击 → 按钮进入 loading
     → fetchPackageLabel([pkg.id])
     → URL.createObjectURL(blob) → window.open(url) 新标签展示 PDF
     → 弹确认框「面单已打开,确认打印完成并流转交运?」
        ├─ 确认 → markPrinted(pkg.id)(现有接口)→ 刷新列表/Tab
        └─ 取消 → 不流转(可重复打印,缓存命中秒开)
     → revokeObjectURL(延时释放,给新标签加载留时间)
```

**B. 批量打印(`wait_ship`** **Tab 工具栏)**

Tab 栏右侧新增「批量打印面单」按钮(与「从妙手同步」按钮同位置风格):

```
点击(仅 wait_ship tab 可见) → 取当前筛选结果包裹(跨页聚合)
     → 按 store_id 分组,组内 >20 再切子组
     → 逐组 await fetchPackageLabel(ids) → 每组一个新标签
     → 进度提示「第 x/y 组:店铺名(n 单)…」(复用现有 toast/进度条样式)
     → 全部成功 → 弹确认「共 N 组面单已打开,确认全部流转交运?」
        ├─ 确认 → 逐个 markPrinted → 刷新
        └─ 取消 → 保留状态,后续行内单独处理
     → 任一组失败(如 aren't ready)→ 该组跳过并 toast 报错,其余组继续(部分成功语义)
```

范围见决策 D5。

**C. 状态展示增强**

详情弹窗展示 `waybill_printed_at` 时间;「已发货」tab 订单可从详情重新拉面单(缓存命中)用于补打。

### 4.5 关键决策点(需确认)

| #  | 决策       | 推荐                                 | 备选                                                                      |
| -- | -------- | ---------------------------------- | ----------------------------------------------------------------------- |
| D1 | PDF 打开方式 | `window.open` 新标签 → 用户 Ctrl+P      | 内嵌隐藏 iframe + `iframe.contentWindow.print()` 自动弹打印框(更接近妙手一键体验,但浏览器兼容性差) |
| D2 | 面单缓存     | 文件缓存、不过期、`refresh` 参数兜底            | 不缓存(每次实时拉,Ozon 限流风险)                                                    |
| D3 | 打印后流转    | 前端确认后调现有 `markPrinted`(打印成功与否由人判断) | 后端拉取成功即自动流转(风险:用户没真打印,状态已走)                                             |
| D4 | 原按钮      | 拆成「打印面单」+「仅标记交运」                   | 直接替换(丢失纯标记能力,补打场景受影响)                                                   |
| D5 | 批量范围     | 当前 tab 全部匹配(跨页,前端逐页聚合 ids)         | 仅当前页(简单,但多页需手动翻页多次)                                                     |

### 4.6 安全与权限

- 路由挂在现有 `authMiddleware`(`x-api-key` / Bearer)之后,与 order-process 其他接口一致;

- PDF 响应不落公共路径,经鉴权接口下发;

- `data/waybills/` 加入 `.gitignore`(对齐 `src/public/` 处理)。

### 4.7 日志与可观测

- 每次拉取记录:`{ storeId, postings: n, cacheHit, durationMs }`(pino,tag `[package-label]`);

- 失败记录 Ozon 原始 message(便于诊断 aren't ready / 权限问题)。

## 6. 实施计划(任务拆分,含依赖)

```
T1. OPI callRaw + packageLabel          (无依赖,可独立验证:node 脚本真调一次)
T2. waybill-cache 服务                   (依赖 T1 的目录约定;独立单测)
T3. POST /package-label 路由            (依赖 T1+T2;curl 验证:单店≤20、混店铺400、缓存命中)
T4. 前端 postBlob + fetchPackageLabel    (依赖 T3 联调)
T5. 行级「打印面单」按钮 + 确认流转      (依赖 T4)
T6. 批量打印(分组/串行/部分失败)        (依赖 T5;最后做,复杂度最高)
T7. 联调 + 真实打印机走查               (全链路:wait_ship 单 → 打印 → 流转 → Tab 计数刷新)
```

验证顺序遵循小批量先行:T1 先用 1 个真实 posting\_number 验证 Ozon 返回 PDF(注意选装配完成 >60s 的订单,避免 aren't ready 干扰);T3 curl 验证缓存命中/refresh;T5 行级打通后再铺 T6 批量。

## 7. 测试要点

| 场景                  | 预期                                     |
| ------------------- | -------------------------------------- |
| 单包裹打印(wait\_ship)   | 新标签出 PDF,确认后流转 ship\_success,Tab 计数 +1 |
| 重复打印同一包裹            | 第二次秒出(缓存命中,日志 cacheHit=true)           |
| 装配后立即打印             | 409 aren't ready,toast 提示稍后重试          |
| 混店铺选中批量             | 前端正确分组,每组独立 PDF                        |
| 20+ 单批量             | 自动切 ≤20 的子组                            |
| Ozon 网络超时           | 沿用 OPI 超时错误,toast 展示,状态不流转             |
| 未配置 credentials 的店铺 | 明确报"店铺未配置 sync\_credentials"           |
| 打印取消(不确认)           | 状态保持 wait\_ship,可再次打印                  |
| 已流转包裹补打             | 详情中仍可拉面单(缓存或重拉),不影响状态                  |
