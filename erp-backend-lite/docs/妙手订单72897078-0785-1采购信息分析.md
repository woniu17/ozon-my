## B三、采购金额分析(关键:非自动同步场景)

该订单 `isAutoRsyncPurchasePayment = "0"`,与订单 A 的 `=1` 形成对比,出现**金额不一致**问题:

| 数据源                                      | 值        | 说明                                    |
| ---------------------------------------- | -------- | ------------------------------------- |
| 妙手采购单 `purchaseOrderPayment`             | **4.07** | 采购单实际支付金额(妙手 raw\_json)               |
| 本地 `miaoshou_purchase.payment_amount`    | **4.07** | 与采购单一致                                |
| 妙手包裹级 `miaoshou_package.purchase_amount` | **9.68** | 妙手主列表接口的 CNYPurchasePrice(与采购单实付不一致!) |

### 金额不一致原因分析

- `isAutoRsyncPurchasePayment=0` 表示妙手**未**自动把采购单金额同步到包裹级

- 妙手包裹级 `purchase_amount=9.68` 来自妙手主列表接口的 CNYPurchasePrice,可能是:

  - 历史采购单金额(采购单被改价前 9.68,后改为 4.07 但未同步)

  - 或妙手某种预估/估算值

- 采购单实际付款 4.07 是真实金额

### 正确的采购金额取值

非自动同步场景下,妙手包裹级 `purchase_amount` **不可信**,应使用采购单 `payment_amount` 按关联包裹数分摊:

```
该订单:1采购单 → 1包裹,分摊 = 4.07 / 1 = 4.07
```

对照本地兜底链(项目记忆):

1. **分摊值**(`SUM(payment_amount / 关联包裹数)`)优先 → 本单应为 4.07
2. 妙手包裹级 `purchase_amount` 兜底 → 9.68(此场景下不可信,会被兜底链跳过)
3. `op_package.total_purchase_amount` 最终兜底

## D六、分析结论

1. **拼单场景确认**:1采购单(114.50)→ 2包裹,妙手已按 Ozon 订单金额比例分摊(68.7 + 45.8 = 114.50 ✓)。

2. **妙手分摊正确性**:68.7/45.8 ≈ 1.5,111.87/74.58 ≈ 1.5,比例一致,分摊合理精确。

3. **raw\_json 只指向订单1**:采购单 raw\_json 的 `platformOrderSn`/`opOrderPackageId`/`relateOpOrderItemIds` 只指向 51673458-0395-1,但中间表 miaoshou\_package\_purchase\_map 关联了2个包裹(说明采集时两个包裹都提取到了同一采购单)。

4. **兜底链设计缺陷(关键发现)**:

   - 当前兜底链"分摊值优先"在拼单场景下取均摊(57.25),**覆盖掉妙手已正确分摊的 68.7/45.8**

   - `isAutoRsyncPurchasePayment=1`(自动同步)时,妙手包裹级值是妙手已分摊好的精确值,**应优先于均摊**

   - 均摊算法只在 `isAutoRsyncPurchasePayment=0`(非自动同步)且妙手包裹级值不可信时才该用

5. **正确的兜底链应该**:

   - `isAutoRsyncPurchasePayment=1`(自动同步):妙手包裹级 `purchase_amount` 优先(妙手已分摊)

   - `isAutoRsyncPurchasePayment=0`(非自动同步):分摊值 `payment_amount / 关联包裹数` 优先(妙手未分摊,需均摊)

   - 手工单(payment\_amount=0):回退妙手包裹级,再回退 op\_package

| 包裹               | 妙手包裹级 purchase\_amount | 分摊值(均摊)                               | 差异        |

### 关键发现

1. **妙手包裹级总额只有 27.00**:8.1+8.1+2.7+8.1=27.00,正好等于采购单3的 payment\_amount=27.00
2. **妙手包裹级只含采购单3的分摊**,完全漏掉了采购单1(41.75)和采购单2(52.10)
3. **分摊值总额 120.85**:30.2125×4=120.85=41.75+52.10+27.00,总额正确
4. **均摊不精确**:4个包裹均摊30.2125,但订单金额差异大(0030-3只有34.69,其他104.07),理想应按订单金额比例分摊

### 兜底链命中分析

| 兜底级别       | 取值              | 是否正确              |
| ---------- | --------------- | ----------------- |
| 1. 分摊值(均摊) | 30.2125         | ✓ 总额正确(分摊不精确但最不坏) |
| 2. 妙手包裹级   | 8.1/8.1/2.7/8.1 | ❌ 严重不准(只含采购单3)    |

**结论**:M:N全连接场景下,妙手包裹级 purchase\_amount **严重不准**(只含部分采购单),必须用分摊值 SUM。

  **判断依据:包裹关联的采购单数(非 isAutoRsyncPurchasePayment)**

  isAutoRsyncPurchasePayment=1 **不能**作为妙手包裹级可信的判断依据(订单 E/F 反证:isAuto=1 但妙手包裹级只含部分采购单)。真正的判断依据是包裹关联的采购单数。

  **分支 A: 包裹只关联1个采购单(1对1 或 1采购单→N包裹拼单)**

  妙手包裹级已包含完整分摊,优先用:

  1. 若 isAutoRsyncPurchasePayment=1:**妙手包裹级** `miaoshou_package.purchase_amount` 优先(妙手已分摊,如订单 A/D)
  2. 若 isAutoRsyncPurchasePayment=0:**分摊值** `SUM(payment_amount / 关联包裹数)` 优先(妙手包裹级不可信,如订单 B)
  3. 若分摊值=0(手工单 payment\_amount=0):**回退妙手包裹级**(唯一来源,如订单 C)
  4. `op_package.total_purchase_amount` 最终兜底

  **分支 B: 包裹关联多个采购单(组合 或 M:N全连接)**

  妙手包裹级可能只含部分采购单,**必须用分摊值**:

  1. **分摊值** `SUM(miaoshou_purchase.payment_amount / 关联包裹数)` 优先(包含所有采购单,如订单 E/F)
  2. `op_package.total_purchase_amount` 最终兜底
  3. **不使用妙手包裹级**(只含部分采购单,不可信)

- **判断逻辑总结**:

  - 包裹关联采购单数 = 1 且 isAuto=1 → 妙手包裹级(订单 A, 订单 D 拼单)

  - 包裹关联采购单数 = 1 且 isAuto=0 且 payment>0 → 分摊值(订单 B)

  - 包裹关联采购单数 = 1 且 payment=0 → 妙手包裹级(订单 C 手工单)

  - 包裹关联采购单数 > 1 → 分摊值(订单 E 组合, 订单 F M:N)

- **物流信息提取规则**(手工单特殊):

  - 平台采集单(1688/拼多多/淘宝):物流在顶层 `purchaseOrderLogisticsName` / `purchaseOrderWaybillCode`

  - **手工单(other)**:顶层为 null,物流在 `purchaseOrderPackages[0].purchaseOrderLogisticsName` / `purchaseOrderWaybillCode`,落地时需从此处提取

  - **平台采购单已发货**:物流在 `purchaseOrderPackages[0]`(如订单 E 圆通/邮政, 订单 F 中通/韵达),顶层为 null

- **手工单识别标志**:

  - `purchasePlatform="other"` + `purchaseOrderSn` 是MD5哈希(非真实单号) + `purchaseOrderDetailUrl="javascript:;"` + `purchasePlatformName=null`

  - 采购单级金额/单价/数量全为 null,唯一金额来源是妙手包裹级 `purchase_amount`

- **拼单识别标志**(1采购单→N包裹):

  - 中间表 `miaoshou_package_purchase_map` 同一 `purchase_id` 关联多个 `package_id`

  - raw\_json 的 `platformOrderSn`/`opOrderPackageId`/`relateOpOrderItemIds` 只指向其中一个包裹(采集来源包裹)

  - `purchaseNum` > 单包裹商品数量(如订单 D 采购3件,包裹1有3件+包裹2有2件)

- **组合识别标志**(N采购单→1包裹):

  - 中间表 `miaoshou_package_purchase_map` 同一 `package_id` 关联多个 `purchase_id`

  - 妙手包裹级 purchase\_amount 可能只含部分采购单(如订单 E 只含3.63,漏3.80)

  - raw\_json 的 `platformOrderSn`/`opOrderPackageId` 指向该包裹,但其他采购单的 raw\_json 也指向同一包裹

- **M:N全连接识别标志**:

  - N个包裹全部关联M个采购单,中间表 N×M 行

  - 妙手包裹级 purchase\_amount 严重不准(只含部分采购单,如订单 F 总额27≠120.85)

  - 多个采购单的 raw\_json 的 `platformOrderSn` 可能指向同一包裹(采集来源)
