# 订单处理流程重构 — 状态机设计

> 状态:梳理完成，待实施（2026-11）
> 参与决策:
> - 贴单与交运拆开，所有订单统一走新状态链
> - 必须采购后才可备货（取消"未采购提前备货"）

---

## 1. 背景与目标

现有本地状态机为 4 段式（`wait_process → wait_ship → ship_success → wait_receiver_confirm`），
无法表达"备货 / 贴单 / 发运 / 揽收"的细分阶段；且发运管理（OGL 集运）与个人自发货
两条路径在状态上不一致。

目标流程（用户确认）：

```
ozon订单 → 待采购 → 待备货 → 待贴单 → 待发运 → 交运中 → 已揽收 → 已签收 → 已成功
                                                            ↘ 已取消 / 已退货
```

## 2. 新本地状态机

`op_package.operate_status` 取值：

| 新状态值 | 中文名 | 对应 Ozon 货件状态 | 进入触发 |
|---|---|---|---|
| `wait_process` | 待采购 | 任意（通常 `awaiting_packaging`） | Ozon 订单同步入库 |
| `wait_stock` | 待备货 | `awaiting_packaging` | 提交采购信息 |
| `wait_stick` | 待贴单 | `awaiting_registration` | 备货成功 |
| `wait_dispatch` | 待发运 | `awaiting_deliver` | 打印面单完成 |
| `dispatching` | 交运中 | `awaiting_deliver`（已确认发运未揽收） | 确认发运 / 扫描发货交运 |
| `delivering` | 已揽收 | `delivering` / `driver_pickup` | Ozon 同步 |
| `signed` | 已签收 | `delivered` | Ozon 同步（写 delivered_at） |
| `settled` | 已成功 | `delivered`（应计含 type_id=67） | 应计同步 |
| `cancelled` | 已取消 | `cancelled` / `not_accepted` | Ozon 同步（吸收态） |
| `returned` | 已退货 | —（`is_returned=1`） | 退货接口同步 |

前进序（只前进不回退）：

```
wait_process(0) < wait_stock(1) < wait_stick(2) < wait_dispatch(3)
< dispatching(4) < delivering(5) < signed(6) < settled(7)
cancelled / returned：独立，任意状态可进，进入后不退出
```

## 3. 流转触发规则

| 流转 | 触发动作 | 说明 |
|---|---|---|
| 待采购 → 待备货 | 提交采购信息 | `submitPurchase` 推进目标改为 `wait_stock` |
| 待备货 → 待贴单 | 点击「备货」 | 备货接口仅允许 `wait_stock`（已采购）操作；成功后主动推进 `wait_stick` |
| 待贴单 → 待发运 | 打印面单 | 只写 `waybill_printed_at`，推进 `wait_stick → wait_dispatch`，不再直接交运 |
| 待发运 → 交运中 | 确认发运（OGL 集运）/ 扫描发货交运（个人自发货） | `carriage/approve` 成功、`scanShipSubmit` 交运成功均推进 `dispatching` |
| 交运中 → 已揽收 | Ozon 同步 `delivering/driver_pickup` | `applyOzonStatus` 推进 `delivering` |
| 已揽收 → 已签收 | Ozon 同步 `delivered` | 推进 `signed`，写 `delivered_at`（保留三取一算法） |
| 已签收 → 已成功 | 应计同步 | 应计含 type_id=67 时推进 `settled` |
| 任意 → 已取消 | Ozon `cancelled/not_accepted` | 吸收态，任意状态可进 |
| 已签收/已成功 → 已退货 | 退货同步 `is_returned=1` | 独立 `returned` |

关键语义决策：

1. **贴单与交运拆开**：打印面单只是"贴单"，不代表交运；交运必须再执行
   确认发运（OGL 集运）或扫描发货提交（个人自发货）。`wait_dispatch` 是两条路径的交汇点。
2. **必须采购后才可备货**：备货接口本地状态校验仅接受 `wait_stock`；
   `wait_process`（未采购）不可备货。原"备货只看 Ozon 状态、与采购进度无关"的
   提前备货语义废除。
3. 本地状态推进由**动作驱动为主**，Ozon 同步负责物流阶段（揽收/签收/取消）的推进。

## 4. 各模块改造点

### 4.1 后端 `src/db/dao/sqlite/order-daos.js`

- `OPERATE_RANK` 表替换为第 2 节的前进序；`cancelled/returned` 保持独立。
- `submitPurchase` 推进目标 `wait_ship → wait_stock`（含批量推进 CASE WHEN 分支）。
- `applyOzonStatus` 分支改写：
  - `delivering/driver_pickup` → `advanceTo('delivering')`（不再写 `wait_receiver_confirm`）
  - `delivered` → `advanceTo('signed')` + 写 `delivered_at` + `shipped_at/is_shipped` 逻辑保留
  - `cancelled/not_accepted` → `cancelled`（不变）
- `markWaybillPrinted`：`CASE WHEN operate_status IN ('wait_process','wait_ship') THEN 'ship_success'`
  改为 `CASE WHEN operate_status = 'wait_stick' THEN 'wait_dispatch' ELSE operate_status END`。
- `tabCounts()`：删除运行时拆分 `wait_receiver_confirm → signed/settled/returned` 的 CASE，
  改为直接按新状态值 GROUP BY；`activeCount` 对应更新。
- 列表查询 `WHERE` 映射：
  - `waitShip → wait_stock`、`shipSuccess → dispatching`
  - `waitReceiverConfirm → delivering`（`delivered_at IS NULL` 条件删除）
  - `signed`、`settled`、`returned` 直接查状态值，不再叠加 `wait_receiver_confirm` 条件
- `revertToWaitProcess`：`wait_ship → wait_process` 改为 `wait_stock → wait_process`。

### 4.2 后端 `src/modules/order-process.js`

- **备货 `ship`**：
  - 本地状态校验：`wait_process/wait_ship` 改为仅 `wait_stock`；
    `wait_process` 返回"请先提交采购信息"。
  - 成功路径（含幂等 `alreadyShipped`、竞态 `HAS_INCORRECT_STATUS` 分支）：
    `syncPosting` 后主动 `UPDATE op_package SET operate_status='wait_stick'`（rank 推进）。
- **打印面单 `print-label`**：推进目标 `wait_stick → wait_dispatch`。
- **扫描发货 `scan-ship/submit`**：`canShip` 校验 `wait_ship → wait_dispatch`；
  提交成功推进 `dispatching`。
- **发运管理 `carriage/approve`**：确认发运成功后，将发运单内所有货件
  `wait_dispatch → dispatching`。

### 4.3 后端 `src/services/order-sync.js`

- 同步推进目标与 `applyOzonStatus` 保持一致（`delivering→delivering`、`delivered→signed`、
  `cancelled→cancelled`）。
- `ozon_postings.status` 仍是推送模型词汇，不需要改；仅本地 `operate_status` 变化。

### 4.4 前端 `web/src/views/OrderProcess.vue`

TABS 更新：

```
全部 / 待采购(waitProcess) / 待备货(waitStock) / 待贴单(waitStick)
/ 待发运(waitDispatch) / 交运中(dispatching) / 已揽收(delivering)
/ 已签收(signed) / 已成功(settled) / 已退货(returned) / 已取消(cancelled) / 已搁置(ignored)
```

- 操作按钮显隐：
  - 待采购：提交采购、备货按钮隐藏
  - 待备货：备货按钮显示
  - 待贴单：打印面单按钮显示（贴单）
  - 待发运：创建/加入发运入口（OGL）、扫描发货入口（个人自发货）
- `TAB_SORT_KEYS`、筛选器（`purchaseUnshippedHours` 等）对应 tab 更新。
- 核心流程注释同步更新。

### 4.5 前端 `web/src/views/ScanShip.vue`

- 扫描发货页仅展示 `wait_dispatch`（原 `wait_ship`）的货件；
- 流程：扫描 → 录重量 → 打印面单（此时已是贴单后的补打）→ 提交交运 → `dispatching`。

### 4.6 发运管理（web `CarriageManage.vue` + 安卓发运管理）

- 候选货件来源状态 `wait_ship/wait_process` → `wait_stock/wait_stick/wait_dispatch` 语义调整；
- 状态文案对齐新状态名（`ContainerLabelFragment.kt` / `CarriageDetailActivity.kt`）。

### 4.7 数据迁移 SQL（实施时按序执行）

```sql
-- 1) 旧 4 段式 → 新状态
UPDATE op_package SET operate_status = 'wait_stock'
 WHERE operate_status = 'wait_ship';

UPDATE op_package SET operate_status = 'dispatching'
 WHERE operate_status = 'ship_success';

-- 2) wait_receiver_confirm 拆分（注意顺序：先 returned → settled → signed → delivering）
UPDATE op_package SET operate_status = 'returned'
 WHERE operate_status = 'wait_receiver_confirm' AND is_returned = 1;

UPDATE op_package SET operate_status = 'settled'
 WHERE operate_status = 'wait_receiver_confirm'
   AND delivered_at IS NOT NULL
   AND id IN (SELECT package_id FROM op_accrual WHERE type_id = 67);

UPDATE op_package SET operate_status = 'signed'
 WHERE operate_status = 'wait_receiver_confirm'
   AND delivered_at IS NOT NULL;

UPDATE op_package SET operate_status = 'delivering'
 WHERE operate_status = 'wait_receiver_confirm';
```

## 6. 风险与注意

- **历史数据**：`wait_receiver_confirm` 拆分依赖 `delivered_at` / `is_returned` / `op_accrual`，
  迁移前先跑一遍 `tabCounts()` 记录旧计数，迁移后核对。
- **`ship_failed` 备货失败**：备货接口失败不推进状态，仍停留 `wait_stock`，前端可重试。
- **发运管理竞态**：`carriage/approve` 与 Ozon 状态同步可能并发，推进用 rank 比较防回退。
- **取消兜底**：`cancel-scanner` 批量对账目标仍是 `cancelled`，不受影响。
